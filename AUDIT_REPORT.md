# Комплексный аудит и архитектурный анализ проекта Balabol

> **Дата проведения анализа:** Октябрь 2026 г.  
> **Роль:** Senior Software Engineer / Solutions & Security Architect  
> **Объект аудита:** Репозиторий `Balabol` (P2P Desktop Voice/Video/Chat на базе Rust + Tauri v2 + Svelte 5).  
> **Активная ветка:** `chat_work`

## 1. Резюме и общее архитектурное состояние

**Balabol** представляет собой интересный и амбициозный P2P-мессенджер, сочетающий современные технологии (**Rust, Tokio, CPAL, Tauri v2, Svelte 5, Tailwind CSS**) и децентрализованный подход к сетевой связности (Full Mesh, STUN, Port Spraying, Nostr NIP-01 сигналинг over WSS).

В проекте есть отличные инженерные решения:
* Качественная реализация Soft-Knee Saturation Limiter и 2:1 FIR-ресэмплера в `audio.rs`.
* Применение NIP-01 WebSocket-сигналинга (Nostr) для обхода необходимости содержать свой сигнальный бэкенд.
* Приятный темный UI в стиле Discord/TeamSpeak.

Однако проект несёт в себе **существенный технический долг, устаревшие рудименты прошлых архитектурных итераций, серьёзные риски производительности и критические уязвимости безопасности**, которые делают его в текущем виде абсолютно непригодным для конфиденциального использования в открытом интернете.

Ниже представлен детальный разбор по категориям:
1. **Мусорный и неиспользуемый код (Dead Code & Clutter)**.
2. **Проблемы стабильности, производительности и архитектурные узкие места**.
3. **Глубокий анализ безопасности и криптографии**.
4. **Рекомендации и пошаговый план модернизации**.

## 2. Мусорный и неиспользуемый код (Dead Code & Clutter)

В процессе эволюции проекта (переход от ручных ссылок-инвайтов к Star-SFU, а затем к Full Mesh Nostr) накопилось значительное количество заброшенного кода, который компилируется в бинарник, раздувает зависимости и вводит в заблуждение разработчиков.

### 2.1. Полностью мёртвые модули и файлы
1. **`desktop/src-tauri/src/invite.rs` (179 строк)**:
   * Модуль целиком является мёртвым кодом (`dead_code`).
   * Функции `create_offer_link`, `create_offer_link_with_id`, `create_answer_link`, `create_answer_link_with_id`, `parse_offer_link`, `parse_answer_link` и структуры `OfferData`, `AnswerData` нигде не вызываются в бизнес-логике. Они использовались в ранней версии для ручной отправки ссылок вида `bala://offer/...`.
   * **Рекомендация:** Полностью удалить файл `invite.rs` и директиву `mod invite;` из `lib.rs`.

## 3. Возможные проблемы, узкие места и баги (Architecture & Reliability)

### 3.1. Монолитный антипаттерн во фронтенде (`App.svelte`)
* Файл `App.svelte` насчитывает **2435 строк** и весит более **101 КБ**.
* В одном файле скомканы: WebAudio-синтез звуков, захват камеры через Canvas/Video, обработка буфера обмена, чат, лайтбокс, настройки аудио, поллинг, отрисовка сетки участников, модальные окна и логи.
* **Последствия:** Тяжелейшая поддержка, высокий риск регрессий, невозможность модульного тестирования компонентов, постоянный перерендеринг всего дерева при обновлении реактивных переменных.
* **Решение:** Декомпозировать на компоненты: `Chat.svelte`, `VideoGrid.svelte`, `AudioSettingsModal.svelte`, `ConnectModal.svelte`, `Lightbox.svelte`, вынести аудио-нотификации в отдельный `soundService.js`.

### 3.2. Критический оверхед IPC: Агрессивный поллинг вместо событий
* В `App.svelte` (строки 225–228):
  ```javascript
  pollInterval = setInterval(pollState, 150); // каждые 150 мс
  videoPollInterval = setInterval(pollVideoFrame, 60); // каждые 60 мс
  ```
* Каждые 150 мс фронтенд делает сразу 4 асинхронных вызова через Tauri IPC:
  1. `get_status`
  2. `get_peers`
  3. `get_chat_messages`
  4. `get_voice_status`
* **Проблема с чатом:** Метод `get_chat_messages` каждые 150 мс **целиком клонирует и сериализует в JSON весь вектор сообщений**, включая Base64-превью картинок! При активном чате на 200+ сообщений это приводит к непрерывной загрузке процессора, сериализации мегабайтов JSON в секунду и задержкам сборщика мусора V8.
* **Проблема с видео:** Видеокадры опрашиваются каждые 60 мс (`pollVideoFrame`), но при этом одновременно на строке 231 зарегистрирован слушатель событий `listen("video-frame")`! Происходит дублирование работы.
* **Решение:** Полностью перейти на Event-Driven архитектуру. Rust должен высылать события `emit("peer-status")`, `emit("chat-message-received")`, `emit("voice-status")` только тогда, когда данные реально изменились.

### 3.3. Нарушение Real-Time Audio Safety в аудио-движке (Priority Inversion)
* В `desktop/src-tauri/src/audio.rs` внутри OS-потока аудио-вывода CPAL (строка 817):
  ```rust
  let mut buffers = peer_buffers.lock();
  let mut chime_q = chimes.lock();
  ```
* Захватывается блокирующий мьютекс `parking_lot::Mutex`. Этот же мьютекс захватывается сетевым потоком при получении UDP-пакетов (`feed_incoming_packet`), при смене громкости (`set_peer_volume`), при получении статуса (`get_audio_diagnostics`).
* Более того, при получении пакетов в `feed_incoming_packet` производятся динамические аллокации памяти в куче (`VecDeque`, `Vec::with_capacity`).
* **Последствия:** Нарушение фундаментального правила разработки аудио-движков — *никогда не захватывать мьютексы и не аллоцировать память внутри аудио-коллбэка реального времени*. При сетевых спайках это гарантированно приводит к инверсии приоритетов, задержкам аудиобуфера, щелчкам и кратковременным зависаниям звука.
* **Решение:** Использовать lock-free кольцевые буферы (Single-Producer Single-Consumer / SPSC, например крейт `rtrb` или `ringbuf`).

### 3.4. Утечки памяти (Memory Leaks)
1. **`image_reassemblers` (`p2p.rs`, строка 1489)**:
   * Если картинка была передана не полностью (потерялся хотя бы 1 чанк по UDP), объект `ImageReassembler` остаётся в хэшмапе `image_reassemblers` **навсегда**.
   * Механизма очистки по таймауту для недособранных картинок нет. Со временем память приложения растет бесконечно.
2. **`image_store` (`p2p.rs`, строка 1499)**:
   * Все полученные полноразмерные изображения сохраняются в `HashMap<String, Vec<u8>>` в оперативной памяти.
   * Нет лимита на количество картинок (LRU Cache), нет ограничения по объему выделенной памяти и нет сброса на диск во временную директорию. Пересылка десятка скриншотов высокого разрешения быстро забьет сотни мегабайт ОЗУ.

### 3.5. Ограничения захвата экрана (`screen_capture.rs`)
* **Только основной монитор:** `GetSystemMetrics(SM_CXSCREEN)` считывает разрешение только основного дисплея. На конфигурациях с двумя и более мониторами окно захватывается со смещениями либо второй монитор полностью недоступен. Нужно использовать `SM_CXVIRTUALSCREEN` / `SM_CYVIRTUALSCREEN`.
* **Устаревший GDI захват:** Функция `StretchBlt` из `GetDC(NULL)` задействует программный рендеринг CPU и блокирует поверхность оконного менеджера DWM. При запущенных современных 3D-играх (DirectX 11/12, Vulkan) GDI-захват приводит к микростаттерам (падению FPS) в игре. Кроме того, некоторые античиты могут блокировать `GetDC`.
* **Решение:** Для Windows стандартом захвата рабочего стола и игр является **Desktop Duplication API (DXGI)** или **Windows Graphics Capture API**.
* **Утечка потока на Linux/macOS:** На других ОС функция `start()` запускает вечный поток, который крутится в бесконечном цикле со `sleep(125ms)`, расходуя ресурсы впустую.

### 3.6. Проблемы логгера (`logger.rs`)
* В методе `AppLogger::log` на **каждое сообщение**:
  ```rust
  OpenOptions::new().create(true).append(true).open(&self.file_path)
  writeln!(file, "{}", formatted)
  file.flush()
  ```
  Синхронное открытие файла на диске, запись и `flush` вызываются прямо из рабочих потоков Tokio! При логировании десятков пакетов в секунду (STUN, NAT-панчинг, фрагменты кадров) диск становится узким местом, блокируя асинхронный рантайм.
* Лог-файл пишется в `std::env::current_dir().join("balabol.log")`. Если приложение установлено в защищенную системную папку (например, `Program Files`), у пользователя без прав администратора приложение упадет с ошибкой `Access Denied`.
* **Решение:** Использовать асинхронный канал логирования (например, крейт `tracing` с фоновым `tracing-appender`) и сохранять логи в системную папку `%LOCALAPPDATA%\Balabol\logs`.

### 3.7. Двойное проигрывание системных звуков
* При подключении к комнате звук проигрывается одновременно в двух местах:
  1. Во фронтенде через Web Audio API (`playConnectSound` в `App.svelte`, строки 288, 133).
  2. В ядре Rust через аудио-драйвер CPAL (`play_connect_chime` в `p2p.rs`, строка 868).
* В результате пользователь слышит задвоенный, рассинхронизированный звук подключения.

### 3.8. Агрессивный Port Spraying (риск сетевых блокировок)
* Функция `expand_candidates_with_port_spray` (`p2p.rs`) распыляет пакеты по 17 соседним портам каждые 2 секунды.
* При 3–4 сетевых адресах узел шлет сотни UDP-пакетов на случайные порты. Корпоративные фаерволы, антивирусы с сетевыми экранами и системы обнаружения вторжений (IDS/IPS) классифицируют такое поведение как сканирование портов (Port Scan) и блокируют IP-адрес узла.

## 4. Анализ безопасности решений (Security & Cryptography Audit)

Это наиболее критическая часть аудита. Архитектура приложения декларирует защищенность, однако на практике содержит фундаментальные уязвимости.

```
+---------------------------------------------------------------------------------------+
|                                МАТРИЦА УЯЗВИМОСТЕЙ                                    |
+--------------------------+---------------------+-------------------+------------------+
| Уязвимость               | Уровень риска       | Тип угрозы        | Сложность атаки  |
+--------------------------+---------------------+-------------------+------------------+
| Отсутствие шифрования UDP| КРИТИЧЕСКИЙ (CVSS 9)| Утечка приватности| Тривиальная      |
| Утечка через Nostr WSS   | КРИТИЧЕСКИЙ (CVSS 9)| Массовый шпионаж  | Тривиальная      |
```

### 4.1. КРИТИЧЕСКИЙ РИСК: Полное отсутствие шифрования P2P UDP трафика
* **Суть проблемы:**
  В файле `desktop/src-tauri/src/p2p.rs`:
  ```rust
  impl Packet {
      pub fn encode(&self) -> Result<Vec<u8>, bincode::Error> {
          bincode::serialize(self)
      }
      pub fn decode(buf: &[u8]) -> Result<Self, bincode::Error> {
          bincode::deserialize(buf)
      }
  }
  ```
* Все сетевые пакеты упаковываются чистым `bincode` **без какого-либо сквозного шифрования (E2EE)**.
* **Что передается в открытом виде:**
  1. Несжатый студийный голос (16-бит 24 кГц PCM) — восстанавливается в звуковой файл за 1 секунду.
  2. Весь текст переписки чата (`Packet::TextMessage`).
  3. Все прикрепленные изображения и скриншоты (`Packet::ImageChunk`).
  4. Видеокадры веб-камеры и трансляции рабочего стола (`Packet::VideoChunk`).
  5. Реальные IP-адреса и никнеймы участников.
* **Вектор атаки:** Любой участник в той же локальной сети (Wi-Fi в кафе, общежитие, офис), провайдер интернета (ISP) или любой узел на пути следования пакетов может открыть Wireshark / `tcpdump` и слушать все разговоры, читать чат и просматривать стримы экранов без малейших усилий.

### 4.2. КРИТИЧЕСКИЙ РИСК: Публичная утечка приватных данных через Nostr WSS релеи
* В `signaling.rs` (строка 711) реализована передача пакетов через публичные Nostr-релеи (`wss://relay.damus.io`, `wss://nos.lol`, `wss://nostr.mom` и др.) в качестве фолбэка:
  ```rust
  let b64 = BASE64.encode(&bytes);
  let payload = format!("bala://pkt/{}", b64);
  let evt = create_signed_event(
      &keypair,
      20001,
      vec![
          vec!["t".into(), relay_tag.clone()], // balabol_p2p_<код_комнаты>
          vec!["s".into(), my_name.clone()],
      ],
      &payload,
  );
  ```
* **Суть проблемы:**
  * Публичные Nostr-релеи — это открытые базы данных, доступные абсолютно любому человеку в мире.
  * Трафик не шифруется! Данные пакета просто кодируются в Base64 (`bala://pkt/{BASE64}`).
  * Подпись `schnorr::sign` лишь доказывает, что сообщение подписано эфемерным ключом, но **не защищает данные от чтения**.
* **Вектор атаки:** Любой желающий может подключиться к `wss://nos.lol` или `wss://relay.damus.io`, подписаться на события с фильтром `#t: ["balabol_p2p_*"]` и в реальном времени собирать историю всех комнат, IP-адреса пользователей, текстовые сообщения и голосовые пакеты.

### 4.3. ВЫСОКИЙ РИСК: Слабые коды комнат и отсутствие изоляции (Room Sniping)
* Код комнаты представляет собой 6 случайных цифр (например, `757805`).
* Всего существует **1 000 000 возможных комбинаций**.
* Злоумышленник может за пару минут просканировать все активные комнаты через WebSocket-фильтры Nostr (War Dialing), узнать список участников и подключиться к приватной конференции без ведома создателя. Пароли комнат или разделяемые секреты отсутствуют.

### 4.4. ВЫСОКИЙ РИСК: Полное отсутствие проверки подлинности и целостности пакетов (Spoofing & DoS)
* В обработчике `handle_mesh_packet` пакет принимается от любого источника без криптографической аутентификации (нет HMAC, нет AEAD-тегов Poly1305/GCM, нет постоянных открытых ключей пиров).
* **Векторы атак:**
  1. **Принудительный дисконнект (DoS):** Злоумышленник посылает на открытый UDP-порт узел поддельный пакет `Packet::Disconnect { sender_id, reason }`. Узел немедленно удалит пира из списка активных и оборвет связь.
  2. **Спуфинг чата:** Отправка `Packet::TextMessage` от имени любого `sender_name` и `sender_id`.
  3. **Аудио-инжекция:** Отправка вредоносных пакетов `Packet::AudioData` — возможность транслировать в уши участников оглушительный шум или посторонние звуки.
  4. **Подмена никнеймов:** Отправка `Packet::NicknameUpdate`.

### 4.5. ВЫСОКИЙ РИСК: Отключенная политика безопасности CSP в Tauri
* В `desktop/src-tauri/tauri.conf.json`:
  ```json
  "security": {
    "csp": null
  }
  ```
* Полное отключение Content Security Policy (`csp: null`) снимает защиту WebView2 от исполнения вредоносных скриптов.
* Если вредоносный пользователь передаст в чат текст или никнейм со специально сформированным HTML/JS (XSS), скрипт выполнится в контексте доверенного окна Tauri. Злоумышленник получит доступ к `window.__TAURI_INTERNALS__` и сможет вызывать нативные системные команды приложения.

### 4.6. СРЕДНИЙ РИСК: DoS через исчерпание памяти (Out-Of-Memory Crash)
* В `ImageReassembler::new` (`p2p.rs`):
  ```rust
  pub fn new(chunk_total: u32) -> Self {
      Self {
          chunk_total,
          chunks: vec![None; chunk_total as usize],
          created_at: Instant::now(),
      }
  }
  ```
* Если атакующий отправит пакет `Packet::ImageChunk` со значением `chunk_total = 2_000_000_000`, приложение выделит вектор гигантского размера в памяти и моментально завершится аварийно (`panic! memory allocation failed`).

## 5. Итоговая сводка и рекомендации к действию

### Шаг 1. Очистка от мусорного кода (Dead Code Cleanup)
1. **Удалить:** `desktop/src-tauri/src/invite.rs` и убрать `mod invite;` из `lib.rs`.
2. **Очистить `signaling.rs`:** удалить `start_host_session`, `HostSignalingSession`, `host_exchange`, `client_exchange`, `MqttSignaling`.
3. **Очистить `p2p.rs`:** удалить неиспользуемые варианты enum `Packet` (`ConnectRequest`, `ConnectAccept`, `ConnectReject`, `PeerListUpdate`, `HostHandover`, `ClaimHost`), поля `backup_host_id`, `next_peer_id`, `pending_acks` и заглушки `transfer_host`, `promote_to_host`.
4. **Очистить `audio.rs`:** удалить неиспользуемую структуру `G711`.
5. **Очистить `Cargo.toml`:** удалить неиспользуемые зависимости `igd-next` и `thiserror`.
6. **Очистить `App.svelte`:** убрать неиспользуемые импорты иконок (`ShieldCheck`, `LayoutGrid`, `Bell`, `Crown`).
7. **Исправить кодировку:** перезаписать битые кириллические строки (Mojibake) в `p2p.rs`.
8. **Очистить Git:** добавить `dist-release/`, `test_logs/` и `*.log` в `.gitignore`, удалить бинарник `balabol.exe` из репозитория.

### Шаг 2. Устранение уязвимостей безопасности (Security Hardening)
1. **Внедрить сквозное шифрование (E2EE):**
   * Использовать современный протокол аутентифицированного шифрования (AEAD) — **ChaCha20-Poly1305** или **AES-256-GCM** (крейт `chacha20poly1305`).
   * Из 6-значного кода комнаты (или пароля) генерировать 256-битный сессионный ключ через **HKDF-SHA256** или **Argon2id**.
   * Шифровать полезную нагрузку (`payload`) всех пакетов (аудио, видео, чат, картинки) перед отправкой как по UDP, так и через Nostr-релеи.
2. **Включить валидацию пакетов:**
   * Проверять AEAD-тег подлинности каждого пакета. Пакеты с неверным тегом должны немедленно отбрасываться без обработки, что полностью исключит DoS-подмену команд `Disconnect`, чата и аудио.
3. **Ограничить выделение памяти в чанках:**
   * Установить лимит `chunk_total <= 5000` (макс. 6 МБ на картинку). При превышении немедленно отбрасывать пакет.
   * Добавить очистку `image_reassemblers` по таймауту (например, удалять через 15 секунд, если картинка не собралась).
   * Ограничить размер `image_store` (хранить не более 20 последних изображений).
4. **Включить Content Security Policy:**
   * В `tauri.conf.json` настроить строгую политику CSP (разрешить только `self` и `data:` для изображений).

### Шаг 3. Архитектурная оптимизация и исправление багов
1. **Рефакторинг `App.svelte`:**
   * Разбить монолит на изолированные Svelte-компоненты.
2. **Замена поллинга на события (Event-Driven IPC):**
   * Убрать `setInterval(pollState, 150)` и передачу полного массива чата через IPC.
   * В Rust генерировать событие `emit("new-chat-message", msg)` при поступлении нового сообщения.
3. **Lock-Free буферы в аудио:**
   * Заменить `parking_lot::Mutex` в коллбэке CPAL на lock-free очередь (например, `rtrb` или `ringbuf`).
4. **Асинхронный логгер:**
   * Перевести `AppLogger` на фоновую запись (крейт `tracing` + `tracing-appender`), писать логи в `%LOCALAPPDATA%\Balabol\logs`.
5. **Модернизация захвата экрана:**
   * Заменить устаревший GDI `StretchBlt` на Windows Desktop Duplication API (DXGI) для повышения FPS и поддержки нескольких мониторов.
6. **Устранить дублирование звуков:**
   * Оставить проигрывание системных звуков только в одном месте (рекомендуется в нативном Rust через CPAL).
