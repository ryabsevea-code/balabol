## 1. Резюме текущего состояния безопасности

В ходе глубокого повторного аудита кодовой базы проекта **Balabol** была произведена комплексная оценка архитектуры безопасности, сетевых протоколов, криптостойкости, устойчивости к атакам (DoS/Spoofing/Replay) и уровня приватности пользователей.

### 1.1. Ключевые изменения и устраненные критические уязвимости:
1. **Внедрено аутентифицированное сквозное шифрование (E2EE):**
   * Все типы трафика (несжатый голос 24 кГц PCM, текстовые сообщения, полноразмерные изображения, кадры рабочего стола/вебкамеры и служебные сигналы) упаковываются в защищенный сетевой контейнер `BALA` на базе **ChaCha20-Poly1305 (IETF RFC 8439)**.
   * Открытый нешифрованный `bincode` ликвидирован. Пакеты, не прошедшие проверку подлинности 128-битного тега Poly1305, отбрасываются до этапа десериализации.
2. **Нейтрализован сетевой спуфинг и принудительный DoS:**
   * Сторонние узлы в сети больше не могут отправить поддельный `Packet::Disconnect`, инжектировать аудио-помехи в голосовой канал или подделывать сообщения в чате.
3. **Ослепление и шифрование сигнального протокола Nostr WSS:**
   * Открытые топики комнат `#t: balabol_mesh_v5_<код>` заменены на необратимый 24-символьный хэш-идентификатор `derive_nostr_topic`. Наблюдатели на публичных Nostr-релеях лишены возможности мониторить коды создаваемых комнат.
   * Анонсы `MeshAnnounce` (содержащие IP-адреса и никнеймы) зашифрованы сессионным ключом комнаты через ChaCha20-Poly1305. Нешифрованные анонсы отклоняются.
4. **Устранена уязвимость OOM DoS при передаче медиа-данных:**
   * Введены строгие лимиты в сборщиках чанков: `ImageReassembler` ($\le 5000$ чанков, размер чанка $\le 4096$ Б) и `VideoReassembler` ($\le 500$ чанков, $\le 4096$ Б).
   * Реализован таймаут сборки (15 сек для изображений, 800 мс для видеокадров).
   * Хранилище `image_store` ограничено LRU-кэшем на 30 объектов и принудительно очищается при `disconnect()`.
5. **Включена строгая политика безопасности контента (CSP):**
   * В `tauri.conf.json` активирован строгий CSP (`default-src 'self'; img-src 'self' data: blob:; media-src 'self' blob:; style-src 'self' 'unsafe-inline'; font-src 'self' data:; connect-src 'self' wss: https:;`).
6. **Изоляция локальных данных и санитизация логов:**
   * Логи (`balabol.log`) и дисковый кэш комнат (`balabol_room_cache.json`) перенесены из директории проекта в системный каталог `%LOCALAPPDATA%\Balabol`.
   * Из дисковых логов удален открытый текст сообщений пользователей (фиксируется только метаинформация: отправитель и длина сообщения в символах).
7. **Полная санитарная зачистка Git-репозитория и GitHub Origin:**
   * Инструментом `git-filter-repo` из всей истории коммитов навсегда удалены бинарные файлы (`Balabol_1.0.0_x64-setup.exe` 43.4 МБ, `balabol.exe` 12.2 МБ), скриншоты тестирования (`test_logs/`) и макетные БД с хэшами паролей.
   * Объем репозитория уменьшен с **60.5 МБ до 0.35 МБ** (сокращение на 99.4%).
   * Все коммиты автора переписаны с анонимным email `ryabsevea-code@users.noreply.github.com`. Удалены устаревшие ветки на GitHub (`star_sfu`, `voice_connection`, `fix-p2p-and-identity-14322536426646908861`).

## 2. Архитектура криптографической защиты (Wire Protocol)

### 2.1. Спецификация сетевого контейнера `BALA`
Каждый UDP-пакет, отправляемый в сеть, упаковывается в унифицированный криптографический конверт:

```
+----------------+--------------------+---------------------------------------+--------------------+
| Magic Header   | CSPRNG Nonce       | Encrypted Payload (Bincode)           | Poly1305 MAC Tag   |
| 4 байта        | 12 байт (96 бит)   | Переменная длина (N байт)             | 16 байт (128 бит)  |
| b"BALA"        | rand::thread_rng() | ChaCha20 Ciphertext                   | Аутентификация     |
+----------------+--------------------+---------------------------------------+--------------------+
```

* **Деривация сессионного ключа:**
  ```rust
  let clean = room_code.chars().filter(|c| c.is_alphanumeric()).collect::<String>().to_lowercase();
  let mut hasher = Sha256::new();
  hasher.update(b"balabol_e2ee_room_key_salt_v1:");
  hasher.update(clean.as_bytes());
  let key: [u8; 32] = hasher.finalize().into();
  ```
  Используется доменное разделение (`balabol_e2ee_room_key_salt_v1:`), предотвращающее пересечение ключей с другими протоколами.
* **Принцип Zero-Trust при приеме пакетов:**
  ```rust
  pub fn decode_wire(buf: &[u8], key_opt: Option<&[u8; 32]>) -> Result<Self, String> {
      if let Some(key) = key_opt {
          if buf.len() >= 32 && &buf[0..4] == b"BALA" {
              let decrypted = crate::crypto::decrypt_packet(buf, key)?;
              Self::decode(&decrypted).map_err(|e| e.to_string())
          } else {
              Err("Rejected unauthenticated packet (E2EE room key active)".into())
          }
      } else {
          Self::decode(buf).map_err(|e| e.to_string())
      }
  }
  ```
  Десериализация `bincode::deserialize` вызывается **исключительно после** успешной криптографической проверки подлинности тега Poly1305. Это исключает эксплуатацию любых потенциальных уязвимостей в парсере bincode внешними неавторизованными источниками.

## 4. Детальный анализ остаточных векторов атак

### 4.1. Вектор 1: Офлайн-перебор сессионного ключа комнаты (Brute-Force / Dictionary Attack)
* **Механика угрозы:**
  * Код комнаты по умолчанию генерируется как 6-значное число в диапазоне `100000..999999` (всего $9 \times 10^5$ комбинаций, что соответствует приблизительно **19.7 битам энтропии**).
  * Функция деривации `derive_room_key` использует одинарный раунд **SHA-256**.
  * Современный графический процессор (например, NVIDIA RTX 4090) способен вычислять свыше $8 \times 10^9$ хэшей SHA-256 в секунду.
  * Если пассивный злоумышленник перехватит хотя бы один зашифрованный сетевой пакет (`BALA` + Nonce + Ciphertext + Poly1305 MAC) или зашифрованный анонс Nostr, полный перебор всего пространства 6-значных кодов комнат займет **менее 1 миллисекунды**.
* **Смягчающие факторы:**
  * Злоумышленник должен физически находиться на пути трафика (ISP, Wi-Fi сниффер) или иметь доступ к слепому топику комнаты на Nostr-релее.
* **Рекомендации по нейтрализации:**
  1. **Замена KDF на ресурсоемкий алгоритм (Argon2id):** Использование `Argon2id` (параметры: $m=64\,\text{MB}, t=3, p=4$) сделает перебор одного пароля вычислительно дорогим (~50 мс на попытку). Перебор 900 000 вариантов займет более 12 часов непрерывной работы кластера GPU.
  2. **Увеличение энтропии кодов комнат:** Переход на буквенно-цифровые фразы (BIP-39 Diceware, 4 случайных слова) либо 10–12-значные алфавитно-цифровые токены (например, `k9x-m2w-87p`), что поднимет энтропию до 60+ бит.

### 4.2. Вектор 2: Атака повторного воспроизведения (Replay Attack)
* **Механика угрозы:**
  * Алгоритм `encrypt_packet` генерирует криптографически случайный Nonce (`rand::thread_rng()`), что надежно защищает ChaCha20 от повторного использования ключевого потока.
  * Однако в структуре `BALA` отсутствует монотонно возрастающий глобальный счетчик пакетов (`packet_sequence_number`), а в `decrypt_packet` отсутствует скользящее окно повторов (Replay Window).
  * На прикладном уровне имеется частичная защита:
    * Текстовые сообщения дедуплицируются по `ChatMessage.id` (`seen_msg_ids`).
    * Аудио-пакеты отслеживаются через `peer_seq_history` (окно на 64 пакета).
  * Однако сетевой атакующий может повторно отправлять валидно зашифрованные пакеты `Packet::Punch`, `Packet::Pong` или аудио-пакеты с задержкой за пределами 64-пакетного окна, вызывая кратковременные искажения звука или сбивая тайминги RTT (пинг).
* **Рекомендации по нейтрализации:**
  * Добавить в заголовок `BALA` 64-битный счетчик пакетов `seq` и внедрить 128-битное скользящее битовое окно (RFC 4303 IPsec Replay Protection).

### 4.3. Вектор 3: Отсутствие Perfect Forward Secrecy (PFS)
* **Механика угрозы:**
  * Все участники комнаты используют общий разделяемый симметричный ключ, напрямую выведенный из кода комнаты.
  * Если код комнаты станет известен третьей стороне post factum (например, через компрометацию устройства одного из участников или утечку переписки), злоумышленник сможет расшифровать **все ранее записанные дампы сетевого трафика (PCAP)** этой сессии.
* **Рекомендации по нейтрализации:**
  * Использовать код комнаты только для первичной взаимной аутентификации (Pre-Shared Key).
  * После установки P2P UDP-канала выполнять эфемерный обмен ключами **Diffie-Hellman на базе Curve25519 (X25519)** с генерацией уникального сессионного ключа на пару участников, стираемого из памяти при отключении.

### 4.4. Вектор 4: Раскрытие внутренней топологии LAN (`gather_candidates`)
* **Механика угрозы:**
  * В методе `gather_candidates` узел опрашивает все локальные физические адаптеры через Windows IP Helper API:
    ```rust
    for extra_ip in find_all_local_physical_ips() {
        let extra_addr = SocketAddr::new(IpAddr::V4(extra_ip), port);
        list.push(extra_addr);
    }
    ```
  * Список адресов рассылается в зашифрованном анонсе Nostr и при PEX-обмене всем участникам комнаты.
  * Если комната объединяет незнакомых пользователей, любой участник получает точные внутренние IP-адреса собеседников (включая корпоративные подсети `10.x.x.x`, `172.16.x.x`, адреса VPN-шлюзов и виртуальных сред Hyper-V/Docker).
* **Рекомендации по нейтрализации:**
  * Ограничить сбор локальных адресов: включать только один активный IP-адрес сетевой карты, через которую проходит маршрут по умолчанию (Default Gateway).
  * Добавить в UI переключатель **«Режим повышенной анонимности»**, исключающий локальные LAN-адреса из анонсов при звонках через интернет.

### 4.5. Вектор 5: Потенциальный DoS через исчерпание CPU (UDP MAC Verification Flood)
* **Механика угрозы:**
  * UDP является протоколом без установления соединения. Злоумышленник, зная IP-адрес и порт узла, может направить поток высокоскоростного UDP-мусора.
  * Каждый пришедший пакет размером $\ge 32$ байт с заголовком `BALA` попадает на вычисление Poly1305 MAC.
  * Хотя пакеты отбрасываются и не десериализуются, при трафике 50 000+ пакетов/сек нагрузка на CPU может вызывать выпадение аудио-кадров и задержки в интерфейсе.
* **Рекомендации по нейтрализации:**
  * Реализовать легкий Token Bucket фильтр на базе кольцевого буфера IP-адресов до вызова криптографических процедур.

### 4.6. Вектор 6: Зондирование Google DNS (`8.8.8.8:80`)
* **Механика угрозы:**
  * В методе `detect_local_lan_ip` используется привязка:
    ```rust
    if socket.connect("8.8.8.8:80").is_ok() { ... }
    ```
  * Хотя реальные пакеты не покидают ОС (сокет лишь запрашивает у стека TCP/IP маршрут к внешнему узлу), хардкод адреса американской корпорации Google (`8.8.8.8`) может вызывать срабатывание систем предотвращения утечек (DLP/EDR) и является признаком плохого тона в анонимном ПО.
* **Рекомендации по нейтрализации:**
  * Использовать нативный Windows API `GetBestRoutes` или `GetBestInterfaceEx` для определения активного интерфейса без обращения к сторонним IP.

## 5. Анализ клиентской безопасности и контейнера Tauri

### 5.1. Анализ поверхности атаки Tauri IPC (32 команды)
* Все 32 зарегистрированные команды в `desktop/src-tauri/src/lib.rs` строго типизированы через Rust serde.
* В кодовой базе отсутствуют вызовы `std::process::Command` (нет возможности командных инъекций в ОС через фронтенд).
* Параметры ввода (`room_code`, `nickname`) санитизируются и фильтруются по допустимым символам.

### 5.2. Content Security Policy (CSP)
* Настроенная директива:
  ```json
  "csp": "default-src 'self'; img-src 'self' data: blob:; media-src 'self' blob:; style-src 'self' 'unsafe-inline'; font-src 'self' data:; connect-src 'self' wss: https:;"
  ```
* Запрещены: исполнение внешних удаленных скриптов, загрузка фреймов, внедрение сторонних объектов. Разрешены только локальные бандлы приложения, Base64-изображения и безопасные WSS-соединения с релеями Nostr.

### 5.3. Защита от XSS во фронтенде (Svelte 5)
* Все текстовые данные пользователей (`{msg.text}`, `{peer.name}`) рендерятся движком Svelte как текстовые ноды DOM. Директива `{@html}` в проекте полностью отсутствует.
* Внедрение XSS-векторов через никнеймы или текст чата невозможно.

## 6. Дорожная карта дальнейшего усиления безопасности (Hardening Roadmap 2.0)

### Приоритет 1 (Криптография и защита от брутфорса):
- [ ] Интеграция **Argon2id** для деривации ключа комнаты из пароля/кода.
- [ ] Поддержка генерации мнемонических 4-словных паролей комнат (BIP-39 Diceware).
- [ ] Внедрение протокола **Noise Protocol Framework (Noise_XX)** или **X25519 ECDH** для Perfect Forward Secrecy между парами узлов.

### Приоритет 2 (Сетевой транспорт и DoS-защита):
- [ ] Добавление 64-битного `seq` в заголовок контейнера `BALA` и 128-битного Replay Window.
- [ ] Реализация Token Bucket rate-limiter на UDP-сокете против flood-атак.
- [ ] Возможность отключения передачи локальных LAN IP-адресов в UI («Режим строгой анонимности»).

### Приоритет 3 (Инфраструктурная независимость):
- [ ] Замена сокетного вызова к `8.8.8.8` на Win32 `GetBestRoute2`.
- [ ] Предоставление пользователю настроек для ввода собственных Nostr-релеев и STUN/TURN серверов.
